# ADR 0006. Хранение истории, заметок и таймеров

- **Статус:** принято
- **Дата:** 2026-10-26
- **Контекст:** P4, FR-12, FR-14

## Контекст

Нужно хранить историю диалога, журнал команд, заметки/дела и таймеры между
запусками. Данные локальные, объём небольшой, конкурирующих процессов нет.
История нужна для контекста LLM (последние 12 реплик) и окна истории.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| SQLite (stdlib `sqlite3`) | транзакции, индексы, ноль зависимостей, in-memory для тестов | ручной SQL и миграции |
| JSON-файлы | просто | гонки, перезапись всего файла, нет запросов |
| TinyDB | простой API | зависимость, медленные выборки, нет типов |
| Postgres | мощно | сервер, избыточно для десктопа |

## Решение

Использовать **SQLite** через stdlib. Схема создаётся идемпотентно в
`storage/db.py` (`CREATE TABLE IF NOT EXISTS`) для таблиц `turns`, `commands`,
`notes`, `timers`. Доступ инкапсулирован репозиториями
(`HistoryRepository`, `CommandRepository`, `NotesRepository`,
`TimerRepository`), SQL не выходит за пределы `storage/`. Соединение одно,
`check_same_thread=False`, запись защищена блокировкой; для тестов доступен
`Database(":memory:")`.

## Последствия

- Нет внешних зависимостей; БД — один файл `data/jarvis.db` (git-ignored).
- Репозитории легко подменить фейками; тесты не трогают диск.
- Схема эволюционирует вручную: при изменении полей нужна миграция или
  пересоздание БД; для текущего объёма данных это приемлемо и задокументировано.
- Таймеры хранят `due_at` и `fired`, но при перезапуске пропущенные
  напоминания не догоняются; это ограничение отмечено в README.
- История ограничена запросами `recent(limit)`; старые записи не удаляются
  автоматически. При необходимости добавляется retention-политика.
